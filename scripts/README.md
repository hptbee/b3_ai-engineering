### Merge Authorization Trust Boundary & Migration

- **Trusted provider boundary:** `b3-guard merge-policy-check` never trusts agent-supplied `PASS`/`MERGED` strings, arbitrary `-BaseSha`/`-MainRef` values, or locally saved JSON receipt files (even with SHA-256 digests). Remote merge authorization (`MERGE_AUTHORIZED`) and post-merge proof (`POST_MERGE_VERIFIED`) require `-PrNumber <N>` and synchronously execute sibling `scripts/b3-github-verify.{ps1,sh}` (read-only `gh api` calls) bound to the local repository's `origin` GitHub slug.
- **PR target vs. policy authority:** Arbitrary valid PR targets (`main`, `develop`, `release/*`, `feature/*`, stacked parents) are resolved from GitHub `base.ref` and live branch tip `live_target_sha` (detecting target movement). Merge policy is always loaded strictly from the base repository's `default_branch` (`policy_authority_sha`), preventing feature or stacked parent branches from self-authorizing via unmerged policy edits.
- **Server-side enforcement remains primary:** Local guards prevent misaligned/prompt-injected agents from treating unverified state as `MERGE_AUTHORIZED`; GitHub server-side branch protection/rulesets and repository permissions remain the authoritative enforcement boundary on merge.
- **Review-ledger migration (`review_independence`):** `review-ledger init` defaults to `review_independence=UNKNOWN` (failing closed on `HIGH`/`CRITICAL` and `merge-policy-check`). Pre-existing `b3-review-ledger-v1` files missing `review_independence=` fail closed as `LEDGER_CORRUPT` on `check` and migrate deterministically to `review_independence=UNKNOWN` via `b3-guard review-ledger -Action normalize -LedgerPath <path>`.

### Receipt migration (`b3-verify-v1`)

Legacy `b3-verify-v1` receipts generated before mode/type/gitlink fingerprinting retain the same schema and header fields, fail closed with `VERIFY_STALE` (exit `2` on `verify-check`, exit `1` `PRECOMMIT_FAIL` wrapping `VERIFY_STALE` on `precommit -RequireVerifyReceipt`), and auto-migrate cleanly when re-verified via `verify-run` (no manual receipt deletion or schema migration step required). Staged-vs-working-tree blob synchronization continues to be enforced by `precommit` while `verify-check` verifies effective working state plus index presence/mode divergence.
