# Subagent dispatch naming (load only at spawn)

This is an on-demand contract for B3 orchestrators, **not** a global rule. Read once only when dispatching; do not copy it into each subagent brief.

- **Canonical roles:** Keep `agents/b3-*.md` filename stems and YAML `name:` stable (for example `b3-reviewer`, `b3-fixer`, `b3-security-reviewer`, `b3-architecture-reviewer`, `b3-performance-reviewer`).
- **Logical aliases:** Prefer `b3-impl-<task-id>` (e.g. `b3-impl-t002`) for implementation and `b3-research-<slug>` for research. Use lowercase ASCII kebab-case and a stable, unique task key; shorten long slugs deterministically if the host imposes a name limit, without collisions.
- **Host fallback:** Request the logical alias as a spawn/display name **only if the host API supports custom names**. Never pass unsupported `Role`/display fields or block dispatch because of naming. A host-generated name is acceptable.
- **Resume:** Keep the logical alias separate from the **host-returned agent ID**, when available. Store that ID in run state and resume by ID, not by alias. If there is no resumable ID, use a fresh agent (or record the existing single-agent independence limitation).
- **Scope:** Apply this convention to B3 subagent identifiers, not ordinary prose, application runtime workers, legacy `.b3/autodev/` checkpoints, or historical decision records. Runtime behavior and reviewer independence take priority over cosmetic naming.
## Optional model preferences

- Read once per dispatch phase (on demand, not globally or per subagent): check `<project>/.b3/models.md`, then `~/.b3/models.md` (or `B3_MODELS_PERSONAL`).
- Applies advisories for `planning`, `implementation`, `b3-reviewer`, `b3-fixer`, and specialist review agents (`b3-security-reviewer`, `b3-architecture-reviewer`, `b3-performance-reviewer`).
- Precedence: explicit user selection > `<project>/.b3/models.md` > `~/.b3/models.md` > native `auto`.
- Dispatch `b3-impl-<task-id>` even for single-task builds when the host supports subagents so a custom `implementation` model applies independently of `main` rather than falling back inline.
- Apply a preferred model **only** when the active host supports selecting a model on dispatch; otherwise inherit the native/parent model. Never block work on missing or malformed preference files, never edit IDE settings or committed `agents/*.md` (`model: inherit`), and never claim a model switch occurred without evidence.

## Automatic wave scheduling

- **Default evaluation:** On every ready queue (`pending`, `depends_on` done), evaluate parallel vs. sequential dispatch automatically — never require the user to ask for parallel agents.
- **4 adaptive isolation modes (least-expensive-safe):**
  1. `SHARED_READ_ONLY`: concurrent read-only research, analysis, evidence verification, and review via `check-wave -Partition` with empty write scopes (`TaskId=none` or `[]`) and declared `-WaveReads`. Concurrent readers run in the existing worktree without temporary files, dummy write paths, separate worktrees, or commits, returning findings directly to Parent; mixed reader/writer waves detect RW conflicts via existing partitioning; preserve reviewer independence and single-writer integration.
  2. `SHARED_DISJOINT_WRITES`: concurrent writers in the same worktree **only** when ALL hold: (a) `check-wave -Partition` (`-WaveReads`, `-ProtectedPaths`, `-IgnoreDirtyPaths`, `-CheckDirtyScope`, `-ExpectedBaseSha`) clears clean disjoint writes with zero RW/dirty/protected conflicts; (b) explicit non-root ownership (`no '.'`); (c) build/test/lint commands cannot collide on shared caches, codegen, or DBs; (d) workers **never** stage, commit, checkout, merge, rebase, stash, or mutate shared Git state; (e) Parent distinguishes **wave-level scope validation** (`mechanical-check -AllowedPaths <wave_owned>`) from **per-worker ownership verification** (`mechanical-check -WaveSpecs <TaskId=owned;...> -WorkerChanges <TaskId=changed;...>` using host-provided edit evidence or attributable changesets) **before** integration/staging, then runs combined `verify-run` + cross-unit review (`review-loop/strategy.md`). Never claim individual worker ownership is verified from a combined diff alone (`UNVERIFIED_COMBINED_ONLY`); when per-worker ownership enforcement is required but host/changeset attribution is unavailable, escalate to `ISOLATED_WRITES` or `SEQUENTIAL` (while preserving `SHARED_DISJOINT_WRITES` for safe ordinary tasks). Declared path ownership != OS filesystem isolation; never claim stronger enforcement than the host provides.
  3. `ISOLATED_WRITES`: separate `git worktree` per writer when justified by high risk, broad/uncertain scopes, colliding build/test side effects, separate branch/commit needs, or insufficient shared-worktree enforcement. Verify every worktree with `b3-guard check-worktree -RepoRoot <wt> -RequireIsolated -ExpectedRoot <parent> -ExpectedBaseSha <sha> -PeerRoots <other_wts>` (Bash: `--require-isolated`). `WORKTREE_OK` verifies worktree identity, not full isolation (parent/peer isolation requires `-RequireIsolated`/`--require-isolated` + `-ExpectedRoot <parent> -PeerRoots <other_wts>` confirming distinct canonical `linked=true`/`isolated=true` worker roots never equal to or nested inside parent or peer worktrees; non-isolation `check-worktree` callers stay intact). Fall back safely (`worktree_identity_failed` → `SEQUENTIAL`) if isolation cannot be established.
  4. `SEQUENTIAL`: automatic fallback when safe/cost-effective parallel execution cannot be established (`single_ready_task`, `trivial_overhead`, `dependency_chain`, `shared_write_conflict`, `read_write_conflict`, `unsafe_shared_side_effects`, `dirty_scope_conflict`, `no_host_isolation`, `sequential_host_fallback`, `malformed_wave_output`, `worktree_identity_failed`, `bounded_concurrency`).
- **Deterministic pre-dispatch & dirty-scope gate:** Before every parallel wave, run `b3-guard.{ps1,sh} check-wave -Partition -WaveSpecs <TaskId=paths;...> [-WaveReads <TaskId=paths;...>] [-ProtectedPaths <csv>] [-IgnoreDirtyPaths <initial_dirty_paths>] [-CheckDirtyScope] [-MaxConcurrency 1..4] [-ExpectedBaseSha <sha>]` (Bash: `--kebab-case`; default `-MaxConcurrency` `3`, cap `4`; `TaskId=none` or `[]` marks pure `SHARED_READ_ONLY` readers):
  - Reject `.` root ownership for concurrent writers; `-ProtectedPaths` guards `.git/`, `.b3/` checkpoints, shared ledgers/manifests, `evidence-index.md`, authority records, and product `single_writer_paths`, resolving/rejecting unsafe symlink/junction aliases.
  - Dirty-scope validation checks staged/unstaged/untracked changes against task writes & reads, preserves `initial_dirty_paths`, and distinguishes pre-existing user changes, authorized worker changes, and unexpected out-of-scope changes before integration (`HEAD` match alone does not prove tree freshness). Block/isolate conflicting tasks while continuing unrelated eligible tasks; never reset or overwrite valid user or worker edits.
- **Strict wave dispatch semantics:**
  - Parse and act strictly on the selected **`wave|N|PARALLEL|agents=<N>|tasks=<csv>|...`** or **`wave|N|SEQUENTIAL|...`** record — **never** infer execution mode from aggregate `WAVE_OK` or `WAVE_PARTITIONED` (supports singleton `wave|1|SEQUENTIAL` followed by `wave|2|PARALLEL`).
  - Dispatch only eligible members of that selected wave; reject malformed/inconsistent guard output (`wave_count`/missing wave/`agents != tasks`/`PARALLEL` with `<2` tasks → `SEQUENTIAL` `malformed_wave_output` or `BLOCKED`).
  - After integrating each wave, **recompute** dependencies, `check-freshness` / dirty scope, and `check-wave -Partition` cleanly before starting the next wave.
- **Host isolation fallback (Cursor, Claude Code, Codex, Antigravity):** If the host lacks parallel subagents or required write enforcement (`check-worktree` for `ISOLATED_WRITES`, or safe shared-worktree separation for `SHARED_DISJOINT_WRITES`), degrade cleanly to `SEQUENTIAL` (`no_host_isolation` / `sequential_host_fallback`) — never report `PARALLEL` when execution was sequential. Read-only units (`SHARED_READ_ONLY`) may still run concurrently when the host supports parallel subagents and outputs stay disjoint.
- **Single-writer integration & partial failure:** Shared state (`progress.md`, `findings.md`, shared ledgers/manifests, authority pins, `review-ledger`) and Git integration (`b3-guard precommit`) remain single-writer in all modes. On partial failure, keep valid verified outputs and isolate/recover only failing units (never `git reset` valid work). Run post-integration `b3-guard verify-run` + cross-unit review (`review-loop/strategy.md`) after parallel code waves.
- **Wave status format (`last_wave:` / report — actual executed concurrency only):**
  - `dispatch=PARALLEL agents=<actual_N> isolation=<SHARED_READ_ONLY|SHARED_DISJOINT_WRITES|ISOLATED_WRITES>`
  - `dispatch=SEQUENTIAL reason=<single_ready_task|trivial_overhead|dependency_chain|shared_write_conflict|read_write_conflict|unsafe_shared_side_effects|dirty_scope_conflict|no_host_isolation|sequential_host_fallback|malformed_wave_output|worktree_identity_failed|bounded_concurrency>`
